# nanoflow

Движок воркфлоу. Граф описывается на YAML или кодом, узел — обычная команда
или функция, стрелка может вести назад.

## Что это

Граф — узлы и стрелки между ними. Движок идёт по стрелкам от узла к узлу и
выполняет каждый. Одно выполнение узла — шаг, весь путь — прогон. Один
запуск графа — сессия, в ней один или несколько прогонов.

- **Узел бывает двух видов.** Рабочий делает работу и передаёт данные
  дальше. Развилка решает, по какой стрелке идти.
- **Узел выполняет команду или функцию.** Команда — любая программа, только
  в YAML. Функция — только в графе кодом и на его языке; программу она
  запускает сама.
- **Стрелка может вести назад:** отказ возвращает работу на доработку.
- **Данные между узлами типизированы.** Проверяет их программа графа: что
  узел вернул обещанное и что это подходит следующему узлу. В YAML типы —
  JSON Schema, в графе кодом — типы его языка.
- **Шаг может идти днями.** Таймаута нет.
- **Прогон может разветвиться** на несколько независимых. Обратно они не
  сливаются.
- **Прогоны не ждут друг друга:** пока один ждёт, например, решения
  человека, остальные идут.
- **В графе нет вычислений:** ни условий, ни подстановок. Всё, что зависит
  от данных, делают узлы.

## Архитектура

- **Движок — отдельная программа на Dart**, одна на все языки графа. Он
  ведёт прогоны: маршрут, разветвление, журнал, восстановление после
  падения. Он же [проверяет граф](#nanoflow-check).
- **[Программа графа](#программа-графа).** Движок получает от неё граф и
  через неё проверяет вход запуска и выполняет шаги; про YAML, языки и типы
  данных он не знает.
- **[Хранение](#хранение) — один формат, две стороны.** Формат один. Движок пишет, UI читает и подписывается на
  изменения.
- **UI — отдельная программа.** Только читает хранилище и рисует граф.

### Пакеты

| Пакет             | Что внутри                                                                                            | Кто использует          |
| ----------------- | ----------------------------------------------------------------------------------------------------- | ----------------------- |
| `nanoflow_model`  | Модели, их JSON-формы и раскладка хранения; проигрывание журнала.                                     | движок и UI             |
| `nanoflow_store`  | Хранилище: запись и чтение своей сессии для `--resume`.                                               | движок                  |
| `nanoflow_reader` | [Читатель](#чтение): чтение и подписка на все сессии графа.                                           | UI                      |
| `nanoflow`        | Библиотека для [графа кодом](#программа-графа): узлы, стрелки, типы, `--graph`, `--input` и `--call`. | программы графа на Dart |

**[Проигрывание журнала](#состояние-прогона)** — вычисление состояния прогона по его событиям:
идёт или закончился, какой шаг текущий, сколько раз его запускали.

Модели, формат и проигрывание — один пакет: это договор между движком и UI,
и его проверяют с двух сторон — сессия, записанная хранилищем, читается
читателем в те же модели.

Граф кодом отдельной программы не требует: файл на Dart с библиотекой
`nanoflow` сам и есть программа графа.

### Репозиторий

Один репозиторий — pub workspace: общий `pubspec.lock` и правила линтера,
каждый пакет и каждая программа — отдельный Dart-пакет.

```text
packages/nanoflow_model/
packages/nanoflow_store/
packages/nanoflow_reader/
packages/nanoflow/

apps/nanoflow_cli/
apps/nanoflow_yaml/
apps/nanoflow_ui/

examples/review/   граф из «Формата» со скриптами узлов
tests/e2e/         nanoflow run на примерах
tool/              скрипты для CI
docs/              ТЗ интерфейса, раскладка графа, макеты
```

- **Пакеты не зависят от программ, программы — друг от друга.**
- **Общий у всех только `nanoflow_model`.** Пакетов вроде `common` нет.
- **`nanoflow_store` и `nanoflow_reader` друг друга не импортируют.** Что
  записанное одним читается другим, проверяет `tests/e2e`.
- **UI не импортирует движок:** только читает `runs` и запускает
  `nanoflow-yaml` и `nanoflow check`.
- **Раскладка графа не импортирует Flutter**, хоть и лежит в UI: её тесты —
  на чистом Dart.
- **У каждого пакета своё:** публичная точка `lib/<имя>.dart`, остальное —
  в `lib/src/`, README и тесты.

## Формат

```yaml
start: collect

types:
  Request:
    {
      type: object,
      required: [branch],
      properties: { branch: { type: string } },
    }

  Change:
    {
      type: object,
      required: [id, path],
      properties: { id: { type: string }, path: { type: string } },
    }

  Report:
    {
      type: object,
      required: [change, findings],
      properties:
        {
          change: { $ref: "#/Change" },
          findings: { type: array, items: { type: string } },
        },
    }

nodes:
  collect:
    command: nodes/collect/run.sh
    in: { $ref: "#/Request" } # вход запуска
    out: { $ref: "#/Change" }
    then: is-empty # безусловный переход

  is-empty: # if
    decide: nodes/is-empty/run.sh
    in: { $ref: "#/Change" }
    then: discard
    else: inspect

  inspect:
    command: nodes/inspect/run.sh
    in: { $ref: "#/Change" }
    out: { $ref: "#/Report" }
    then: verdict

  verdict: # switch
    decide: nodes/verdict/run.sh
    in: { $ref: "#/Report" }
    then:
      accepted: [publish, notify] # разветвление
      returned: fix

  fix:
    command: nodes/fix/run.sh
    in: { $ref: "#/Report" }
    out: { $ref: "#/Change" }
    then: inspect

  publish:
    command: nodes/publish/run.sh
    in: { $ref: "#/Report" }

  discard:
    command: nodes/discard/run.sh
    in: { $ref: "#/Change" }

  notify:
    command: nodes/notify/run.sh
    in: { $ref: "#/Report" }
```

### Граф

| Поле    | Что значит                         |
| ------- | ---------------------------------- |
| `start` | Цель, с которой начинается прогон. |
| `types` | Именованные типы данных.           |
| `nodes` | Узлы: рабочие и развилки.          |

Цель — имя узла или список имён. Каждый узел списка получает те же данные.
Пустой список — никуда: прогон на этом заканчивается.

### Рабочий узел

| Поле      | Что значит                                                      |
| --------- | --------------------------------------------------------------- |
| `command` | Что выполняет узел: команда shell или, в графе в коде, функция. |
| `in`      | Тип данных, которые узел получает. Необязателен.                |
| `out`     | Тип данных, которые узел возвращает. Необязателен.              |
| `then`    | Цель. Без него прогон заканчивается.                            |

### Развилка

| Поле     | Что значит                                                                                   |
| -------- | -------------------------------------------------------------------------------------------- |
| `decide` | Что выполняет развилка, чтобы решить, куда идти: команда shell или, в графе в коде, функция. |
| `in`     | Тип данных, которые читает развилка. Необязателен.                                           |
| `then`   | Цель или карта «исход → цель».                                                               |
| `else`   | Цель, если исход не совпал. Необязателен.                                                    |

Форма `if` — в `then` цель, форма `switch` — в `then` карта.

| Форма    | Исход совпал | Не совпал, `else` есть | Не совпал, `else` нет |
| -------- | ------------ | ---------------------- | --------------------- |
| `if`     | в `then`     | в `else`               | прогон заканчивается  |
| `switch` | в цель ключа | в `else`               | ошибка                |

Исход сравнивается с ключами `then` по точному значению. У `if` ключ один —
`true`: `"true"`, `1`, `null` и всё остальное не совпадают. Пустой
`else: []` — тоже `else`: ошибки нет.

Исходом может быть любое JSON-значение. Данные идут к целям сквозь развилку
без изменений, даже если `decide` их не читает.

### Типы

- **Типы — обычная JSON Schema 2020-12.** В `in` и `out` всегда стоит
  схема; ссылка на тип из `types` — обычная её часть.
- **Совместимость — равенство.** `out` подходит к `in`, если после
  раскрытия ссылок схемы совпадают.
- **В `types` только сущности.** Массив пишется прямо в `in` или `out`
  узла, отдельным типом не объявляется.
- **Ссылка — `#/Имя`.** Это не путь от корня файла графа, как в обычной
  JSON Schema: `#` здесь — содержимое `types`. Программа графа при каждой
  проверке отдаёт валидатору содержимое `types` корнем для ссылок, поэтому
  `#/Change` — это `types.Change`, где бы ссылка ни стояла: в `in`, в `out`
  или внутри другого типа.

## Протокол команды

Команда — обычный Unix-фильтр: вход читает из stdin, результат пишет в
stdout, всё для человека — в stderr. Ни путей, ни переменных окружения
протокол не требует. Готовая программа — `jq`, `claude -p` — становится
узлом графа на YAML без обёртки. В графе кодом её запускает функция узла.

| Поток  | Рабочий узел                                                                 | Развилка                                                             |
| ------ | ---------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| stdin  | Данные от предыдущего узла. Без `in` — пусто.                                | Данные, которые идут сквозь развилку. Без `in` — пусто.              |
| stdout | Данные узла, программа графа сверит их с `out`. Без `out` — лог, как stderr. | Исход: `true` или `"accepted"`. Движок ищет его среди ключей `then`. |
| stderr | Лог.                                                                         | Лог.                                                                 |

Остальное:

- **stdout — один JSON-документ.** Пробелы и перевод строки вокруг него
  допустимы, поэтому `echo '"accepted"'` — законный исход.
- **Сбой** — ненулевой код завершения. То же самое — нулевой код, когда
  stdout ждут, а он пуст, в нём не JSON или данные не проходят `out`. Сбой —
  не исход: прогон он останавливает всегда, `else` его не ловит.
- **stdout проверяет программа графа.** Не прошёл — `--call` завершается с
  ненулевым кодом, а в лог шага пишет ошибку и начало stdout: так видно, что
  туда попало.
- **Потоки идут через движок.** Вход команда получает в stdin, и сразу за
  ним её stdin закрывается. stderr движок дописывает в лог шага по мере
  поступления, stdout копит до завершения; у рабочего узла без `out` —
  дописывает в лог, как stderr.
- **Выход сохраняется только проверенным:** документом он становится после
  кода 0 и проверки, его `id` записывается в `outputId` шага. Где лежат
  вход, выход и лог, команда не знает.

**В shell-скрипте из нескольких команд** stdout общий: результат `git
commit`, `npm install` или отладочного `echo` попадёт в данные. Проще всего
с первой строки отправить всё в лог, а данные писать явно:

```sh
exec 3>&1 1>&2       # дескриптор 3 — прежний stdout, stdout теперь ведёт в лог
git commit -am "wip" # в лог
echo "$result" >&3   # в данные
```

## Программа графа

Программа графа печатает граф, проверяет вход запуска и выполняет шаги.

| Команда                       | Что делает                                                                                                                               |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `<программа> --graph`         | Печатает описание графа (ниже) и завершается. Так граф получают движок, `check` и UI.                                                    |
| `<программа> --input`         | Читает вход запуска из stdin, проверяет его по `in` стартовых узлов и печатает проверенный. Не прошёл — ненулевой код, причина в stderr. |
| `<программа> --call <узел>`   | Выполняет шаг узла: запускает его команду или вызывает функцию. Вход, выход и лог — по [протоколу команды](#протокол-команды).           |
| `<программа> --graph --watch` | Печатает описание графа и потом — каждый раз, когда граф меняется.                                                                       |

Описание графа — один JSON-объект:

| Поле    | Что значит                                              |
| ------- | ------------------------------------------------------- |
| `file`  | Путь к запущенному файлу графа: YAML или исходник кода. |
| `graph` | [Граф](#граф) в JSON, ключи те же, что в YAML.          |

- **`--watch` печатает по описанию на строку**, JSON в одну строку. Пока
  файл графа не разбирается, не печатается ничего: следующее описание придёт
  после исправления.
- **Шаг — отдельный процесс `--call`**, у команды и у функции. Команду
  программа запускает через `sh -c` из выбранного ею каталога, в своей
  группе процессов, чтобы останавливать её вместе с потомками, и отдаёт ей
  свои stdout и stderr.
- **Вход приходит одной строкой.** Движок пишет в stdin `--call` вход —
  JSON в одну строку, без `in` строка пустая — и stdin не закрывает.
  `--call` отдаёт вход в stdin команды и закрывает его: для команды это
  обычный [протокол](#протокол-команды).
- **Шаг умирает вместе с движком.** Конец stdin `--call` значит
  «остановись»: движок закрывает stdin, когда останавливает шаг, а упал
  движок — stdin закрывает ОС. `--call` убивает группу процессов команды и
  завершается. Так же — по SIGINT и SIGTERM: иначе Ctrl+C завершил бы
  `--call`, а команда в своей группе осталась бы жить.
- **YAML** — отдельная программа на Dart: получает файл, команды запускает
  из его каталога. Функций нет.
- **Код** — программа на Dart с библиотекой [`nanoflow`](#пакеты): узлы,
  стрелки и типы пишутся на Dart, `--graph`, `--input` и `--call` реализует
  библиотека. Как это выглядит — в [графе на Dart](docs/dart-graph.md).
- **Функция не знает, как её вызвали:** stdin, stdout и процессы — забота
  библиотеки. Узел графа кодом — всегда функция, команд в нём нет.

## Хранение

Что хранится и какие правила соблюдает любой адаптер хранилища.

### Модели

У модели всегда есть все поля; если значения нет — `null`.

Идентификатор — UUID v4.

#### Сессия

Один запуск графа. Время начала — в `run-started` её прогонов.

| Поле    | Что значит                      |
| ------- | ------------------------------- |
| `id`    | Идентификатор.                  |
| `graph` | Граф на момент создания сессии. |

#### Прогон

Один путь по графу.

| Поле        | Что значит                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------------- |
| `id`        | Идентификатор.                                                                                        |
| `sessionId` | Идентификатор сессии, к которой относится.                                                            |
| `parentId`  | Идентификатор прогона, из разветвления которого создан; из той же сессии. `null` у начатого запуском. |

#### Шаг

Один заход в узел.

| Поле       | Что значит                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- |
| `id`       | Идентификатор.                                                                                                             |
| `runId`    | Идентификатор прогона, к которому относится.                                                                               |
| `inputId`  | Идентификатор документа — входа команды. `null`, если у узла нет `in`.                                                     |
| `outputId` | Идентификатор документа — выхода команды. `null`, пока команда не завершилась с кодом 0, и если у рабочего узла нет `out`. |
| `log`      | Лог команды.                                                                                                               |

Что попадает во вход, выход и лог — в [протоколе команды](#протокол-команды).

#### Документ

Данные, которые передаются между шагами: вход запуска или выход шага.

| Поле        | Что значит                                 |
| ----------- | ------------------------------------------ |
| `id`        | Идентификатор.                             |
| `sessionId` | Идентификатор сессии, к которой относится. |
| `value`     | JSON-значение.                             |

### Правила

- **Ничего не перезаписывается.** Повторный заход в узел — новый шаг.
- **Первый шаг прогона, начатого запуском, создаётся вместе с сессией,**
  до своего `step-started`: его `inputId` — единственная ссылка на вход
  запуска. Движок запускает этот шаг, а не создаёт новый, в том числе при
  `--resume`.
- **Порядок шагов — порядок их первых `step-started` в журнале.**
- **У прогона всегда один исполняемый шаг.**
- **Разветвление создаёт новые прогоны** в той же сессии, а прежний на этом
  заканчивается.
- **Сессию ведёт один процесс движка.** Его шаги умирают вместе с ним
  ([программа графа](#программа-графа)), поэтому при старте незавершённый
  шаг выполняется заново, лог дописывается.
- **Состояние отдельно не хранится:** оно получается проигрыванием журнала
  прогона. Движок в журнал только дописывает.

### События

Событие — отдельная модель. Три поля есть у любого события, остальные
зависят от его имени:

| Поле    | Что значит                                   |
| ------- | -------------------------------------------- |
| `runId` | Идентификатор прогона, к которому относится. |
| `time`  | Время события в UTC, с миллисекундами.       |
| `event` | Имя события.                                 |

#### `run-started`

Прогон создан. Первое событие прогона.

| Поле   | Что значит                          |
| ------ | ----------------------------------- |
| `node` | Узел, с которого прогон начинается. |

#### `step-started`

Команда запускается.

| Поле     | Что значит          |
| -------- | ------------------- |
| `stepId` | Идентификатор шага. |
| `node`   | Имя узла.           |

#### `step-finished`

Команда завершилась. Итог шага записывается только сюда: по нему движок
знает, куда идти дальше, в том числе после падения.

| Поле       | Что значит                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `stepId`   | Идентификатор шага.                                                                                                              |
| `exitCode` | Код завершения процесса шага.                                                                                                    |
| `outputId` | Идентификатор документа — выхода команды: данных рабочего узла или исхода развилки. `null` у рабочего узла без `out` и при сбое. |

Документ выхода записывается до события. Упал движок между ними — шаг не
завершён и выполняется заново, а документ остаётся без ссылки.

#### `run-split`

Путей дальше несколько: цель — список. Пишется после того, как созданы новые
прогоны. Своих полей нет: потомков находят по их `parentId`. Если движок упал
посреди разветвления, после перезапуска он создаёт только недостающих
потомков.

#### `run-finished`

Идти некуда: у узла нет `then` или цель пуста. Своих полей нет.

#### `run-failed`

Сбой команды или ошибка маршрута.

| Поле     | Что значит                                    |
| -------- | --------------------------------------------- |
| `stepId` | Идентификатор шага, на котором это случилось. |
| `error`  | Одна строка о том, что случилось.             |

Шаг с `step-started` без `step-finished` не завершён. Перезапуская его
команду, движок пишет новый `step-started`. `run-split`, `run-finished` и
`run-failed` — последнее событие прогона: без них прогон не закончен.

### Состояние прогона

Результат проигрывания журнала. Не хранится: считается заново по событиям
прогона, событие с незнакомым именем пропускается.

| Поле         | Что значит                                                            |
| ------------ | --------------------------------------------------------------------- |
| `runId`      | Идентификатор прогона.                                                |
| `status`     | `pending`, `running`, `finished`, `failed` или `split` — см. ниже.    |
| `steps`      | Состояния шагов в порядке их первых `step-started`.                   |
| `startedAt`  | Время `run-started`.                                                  |
| `finishedAt` | Время последнего события у закончившегося прогона; `null`, пока идёт. |
| `error`      | `error` из `run-failed`; `null`, если сбоя нет.                       |

| `status`   | Когда                                            |
| ---------- | ------------------------------------------------ |
| `pending`  | Есть `run-started`, но ни одного `step-started`. |
| `running`  | Есть шаги, последнего события прогона нет.       |
| `finished` | Последнее событие — `run-finished`.              |
| `failed`   | Последнее событие — `run-failed`.                |
| `split`    | Последнее событие — `run-split`.                 |

Текущий шаг — последний в `steps`; у `running` он и есть исполняемый.

#### Состояние шага

| Поле         | Что значит                                                                          |
| ------------ | ----------------------------------------------------------------------------------- |
| `stepId`     | Идентификатор шага.                                                                 |
| `node`       | Имя узла.                                                                           |
| `status`     | `running` — нет `step-finished`; `finished` — есть; `failed` — на нём `run-failed`. |
| `starts`     | Сколько раз запускали: число `step-started`.                                        |
| `startedAt`  | Время первого `step-started`.                                                       |
| `finishedAt` | Время `step-finished`; `null`, пока идёт.                                           |
| `exitCode`   | Из `step-finished`; `null`, пока идёт.                                              |

### Чтение

Читатель отдаёт хранение одного графа: ленту изменений и данные по запросу.

**Лента изменений** — сначала всё, что уже есть, потом новое по мере
появления. Изменение — модель: поле `change` с именем изменения, остальные
поля зависят от него:

| `change`         | Когда                                                                   | Свои поля                                                                |
| ---------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `session-added`  | Появилась сессия графа.                                                 | `session` — [сессия](#сессия).                                           |
| `run-added`      | Появился прогон.                                                        | `run` — [прогон](#прогон).                                               |
| `step-added`     | Появился шаг.                                                           | `step` — [шаг](#шаг).                                                    |
| `step-changed`   | У шага появился `outputId`. Единственное изменение уже выданной модели. | `step` — шаг целиком, с новым `outputId`.                                |
| `event-added`    | В журнал прогона дописано событие.                                      | `event` — [событие](#события).                                           |
| `document-added` | Документ записан целиком.                                               | `sessionId`, `documentId`. Значение — по запросу.                        |
| `log-corrupted`  | Строка журнала не разбирается как JSON.                                 | `runId`, `line` — номер строки в журнале, с 1, `text` — строка как есть. |

**По запросу:** граф сессии, значение документа, лог шага — накопленный,
потом дописанное.

- **События одного прогона — в порядке журнала.** Остальное — в любом:
  `step-started` может прийти раньше своего шага.
- **Недописанное событие не выдаётся.**
- **Событие с незнакомым именем выдаётся как есть.**

## Адаптер файловой системы

Хранит сессии в каталогах и файлах.

### Каталог `runs`

Каталог `runs` лежит рядом с файлом графа.

```text
runs/
  workflow-2026-09-20T14-03-11-3f9c2a7e-5b1d-4c8e-9a6f-0d2e4b7c1a35/            сессия
    session.json                                                                поля сессии
    documents/
      8e1f4b2a-6c3d-4f7e-b5a9-2d0c7e6f1b48.json                                 вход запуска
      c4a7e9d1-2f5b-4a6c-8e3d-9b1f0a7c5e62.json                                 выход collect
    2026-09-20T14-03-11-470-7d2b9e4f-1a6c-4b3e-8f5d-6c0a2e9b4d17/               прогон
      run.json                                                                  поля прогона
      log.jsonl                                                                 журнал событий прогона
      steps/
        2026-09-20T14-03-11-482-collect-5a8c1e3f-7b2d-4e9a-a6c4-1f3d8b0e2c59/   шаг
          step.json                                                             поля шага
          command.log
        2026-09-20T14-05-40-117-is-empty-0b6d2f9a-4e8c-4a1b-9d7e-3c5f6a2b8e04/
    2026-09-20T14-09-52-310-e2c5a8f1-9d4b-4f6e-b3a7-8c1e0d5f2a96/               прогон после разветвления, устроен так же
```

| Модель   | Где лежит                                                                                                   |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| Сессия   | Каталог `<имя графа>-<время создания>-<id>`; поля — в `session.json`.                                       |
| Прогон   | Каталог `<время создания>-<id>` в каталоге сессии; поля — в `run.json`.                                     |
| Шаг      | Каталог `steps/<время начала>-<узел>-<id>` в каталоге прогона; поля — в `step.json`, лог — в `command.log`. |
| Документ | Файл `documents/<id>.json` в каталоге сессии.                                                               |
| Событие  | Строка JSON в `log.jsonl` каталога прогона, в порядке записи.                                               |

Каталог находят по идентификатору — это последние 36 символов имени. Имя
графа, время и узел перед ним — для человека и для сортировки: сессии графа
находятся по имени, прогоны сортируются по имени в порядке создания, шаги —
в порядке выполнения. Время — в UTC, у прогона и шага с миллисекундами. Эти
части имени движок не читает: всё это есть в журнале.

### Чтение с диска

- **За изменениями читатель следит** по событиям файловой системы и
  подстраховывается опросом: события бывают с задержкой и склеиваются.
- **Журналы и логи дочитываются** с места, где читатель остановился.

## Запуск

```bash
nanoflow run <граф> < вход.json             # создаёт сессию и ведёт её до конца
nanoflow run --resume <сессия> <граф>        # продолжает сессию после падения движка
```

`<граф>` — команда программы графа после `--`:
`nanoflow run -- dart run graph.dart < вход.json`. Для YAML это программа
для YAML с файлом графа.

- **Вход запуска — stdin `run`**, как у команды узла. Если ни у одного узла
  из `start` нет `in`, stdin не читается.
- **Вход проверяется до создания сессии:** движок передаёт его в
  `<программа> --input`, один раз за запуск. Входа нет или он не прошёл —
  `run` завершается с кодом `2`, сессия не создаётся.
- **Проверенный вход — документ.** Вход, который напечатал `--input`,
  движок сохраняет документом, а его `id` пишет в `inputId` первого шага
  каждого прогона, начатого запуском. Других ссылок на вход запуска нет.
- **Сессия создаётся целиком:** документ входа, прогоны, начатые запуском,
  их `run-started` и первые шаги — до первого `step-started`. Упал движок
  раньше — сессии нет.
- **stdout — только идентификатор сессии:** одна строка сразу после её
  создания, у `--resume` тоже. По нему сессию продолжают.
- **stderr — ход сессии для человека:** строка на событие.
- **Сбой прогона не останавливает остальные.** `run` завершается, когда
  закончились все прогоны сессии.
- **`--resume` продолжает сессию** после падения движка. Вход уже
  сохранён, stdin не читается. Законченную сессию `--resume` не выполняет:
  печатает её идентификатор и завершается с её кодом.
- **Граф берётся один раз, при создании сессии,** и сохраняется в ней.
  Сессия до конца идёт по нему, `--resume` тоже.

Код завершения `run`:

| Код       | Когда                                                                                                                                                                                                                     |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`       | Все прогоны сессии закончились, сбоев нет.                                                                                                                                                                                |
| `1`       | Все прогоны закончились, хотя бы один — `run-failed`.                                                                                                                                                                     |
| `2`       | До прогонов не дошло: не те аргументы, программа графа не отдала граф, граф не прошёл `check`, входа нет или он не прошёл `--input`, сессии для `--resume` нет. Сообщение — в stderr, ошибки `check` — по одной в строке. |
| `128 + N` | Движок остановлен сигналом `N`, Ctrl+C — `130`. Шаги останавливаются вместе с ним, сессию продолжает `--resume`, как после падения.                                                                                       |

## `nanoflow check`

`nanoflow check <граф>` — `<граф>` такой же, как у `run`.

Проверяется граф, который вернула программа графа на `--graph`: поле
`graph` её [описания](#программа-графа). Файл графа `check` не читает,
поэтому проверка одна на YAML и код.

Без `<граф>` то же описание читается из stdin. Так проверяет UI: описание он уже
получил от `--graph --watch`, а новый запуск программы графа мог бы вернуть
уже другой граф.

Ошибки — по одной в строке в stdout. Код завершения — 0, если граф прошёл
проверку, иначе 1.

**Структура** проверяется JSON Schema графа в JSON: она ловит опечатки в
ключах и не тот тип значения.

**Смысл**, которого схема не выражает:

- Все цели — в `start`, `then`, `else` — называют существующие узлы.
- В списке целей нет повторов и не одно имя.
- `start` не пуст.
- До каждого узла можно дойти по стрелкам от какого-нибудь узла из `start`.

Тот же код работает при старте: движок не идёт по невалидному графу.

**Типы `check` не проверяет** — это делает программа графа: граф с ошибкой
типов она не отдаёт на `--graph`. Программа для YAML проверяет, что `$ref`
указывает на существующий тип в `types` и что `out` каждого рабочего узла,
из которого можно прийти в узел с `in` — напрямую или сквозь развилки, —
объявлен и совместим с этим `in`; узел без `in` законен после любого. В
графе на Dart то же проверяет компилятор.
