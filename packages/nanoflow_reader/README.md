# nanoflow_reader

Читатель для UI: следит за всеми сессиями в каталоге `runs` и отдаёт ленту
изменений и данные по запросу ([чтение](../../README.md#чтение)). Раскладка —
как в [хранении](../../README.md#хранение). Библиотека пишет те же файлы
пакетом `nanoflow_store`; этот пакет его не импортирует.

## Что внутри

- **`FsReader`** — каталог `runs`. Сессии — каталоги, имя которых подходит
  под `isSessionDirName`, любого воркфлоу. Имена с точкой пропускаются
  везде: под ними хранилище собирает файлы и каталоги.
- **`changes()`** — лента: сначала всё, что уже есть, потом новое. Один
  подписчик; отписка останавливает слежение. Каталога `runs` может ещё не
  быть — лента начнётся, когда он появится. За один проход по дереву, для
  каждой сессии, от новых к старым по времени создания в имени каталога:
  `session-added`, затем новые шаги (`step-added`), новые полные строки
  журнала (`event-added` с `sessionId`), затем новые документы. Новые сессии
  первыми: у длинной истории первым приходит то, что скорее всего будут
  смотреть.
  - Строка журнала без `\n` не выдаётся: место чтения стоит после последней
    полной строки, так что обрезанную при `resume` строку читатель не
    заметит. Если журнал всё же стал короче прочитанного, чтение идёт с конца
    последней оставшейся полной строки, а не с начала файла.
  - Полная строка, которая не JSON-объект со строковыми `time` и `event`, —
    `log-corrupted` с номером строки (с 1) и текстом, один раз; незнакомое
    событие — `event-added` с `UnknownEvent`.
  - `step-changed` — один раз, когда в `step.json` появляется `outputId`,
    который уже есть в `step-finished` этого шага.
  - Файл, который не читается как своя модель, приходит ошибкой в ленту один
    раз; сущность выдаётся, когда файл исправят, остальное идёт дальше.
  - Закончившееся больше не читается: в сессию после её последнего события
    (`session-finished`, `session-failed`) не пишут. Сессия читается ещё один
    проход после того, в котором прочитано последнее событие: проход мог
    перечислить шаги раньше, чем положен последний. Так проход по длинной
    истории стоит почти ничего.
- **По запросу:** `documentValue` и `stepLog` — лог шага: накопленный текст,
  потом дописанный, UTF-8 на стыках кусков не рвётся; пока `step.log` нет,
  ничего не выдаётся. Сущности находятся и до того, как лента их выдала.
- **Пути** — `sessionPath`, `stepPath`, `logPath`, `documentPath`: известны,
  когда лента выдала сущность, до того — `null`.
- **Слежение** — события файловой системы (`Directory.watch`) и опрос раз в
  `pollInterval`: события бывают с задержкой и склеиваются. Проходы не
  накладываются: сигнал во время прохода — ещё один проход после него.
  Запись в `step.log` проход ленты не вызывает: лог идущего шага меняется
  постоянно, а ленте он не нужен — его читает `stepLog`.
