# nanoflow_store

Хранилище сессий библиотеки `nanoflow`: записывает сессию в каталог `runs` и
читает её обратно для `resume`. Раскладка — как в
[хранении](../../README.md#хранение); UI читает те же файлы своим пакетом
`nanoflow_reader`, этот пакет он не импортирует.

## Что внутри

- **`FsStore`** — каталог `runs`. `createSession` создаёт сессию — один вызов
  функции воркфлоу — целиком: `session.json` (воркфлоу, снимок файла графа,
  `inputId`), документ входа (если вход есть), пустой `steps` и `log.jsonl`
  с `session-started` и хэшем кода. `openSession` находит сессию по
  идентификатору и обрезает недописанную последнюю строку журнала.
  `unfinishedSessions(workflow)` — id сессий воркфлоу без `session-finished`
  и `session-failed`, новые первыми; блокировку не берёт, нечитаемые сессии
  пропускает.
- **Сессию ведёт один процесс.** `createSession` до первой записи, а
  `openSession` до обрезки журнала берут исключительную блокировку ОС
  (`fcntl`) одного байта `ownerLockOffset` (`1 << 30`) файла `.owner.lock` в
  каталоге сессии, а не всего файла: содержимое не под блокировкой и
  читается и там, где блокировки обязательные. Блокировка всего файла
  прежней версии этот байт покрывает: они по-прежнему исключают друг друга.
  Держит блокировку `SessionHandle` до `release()` или конца процесса — ОС
  снимает её и с упавшего процесса. Держит другой процесс — `openSession`
  ничего не трогает и бросает `SessionBusyException`. Блокировка `fcntl` — на
  процесс: вторая блокировка того же файла в процессе удаётся, а закрытие
  любого его дескриптора снимает её. Поэтому сессии, которые держит изолят,
  store помнит сам: повторный `openSession` такой сессии бросает
  `SessionBusyException`, не открывая файл блокировки. Другой изолят того же
  процесса это не видит.
- **Владелец в `.owner.lock`.** `FsStore(runsDir, {Owner? owner})`: взяв
  блокировку, store пишет `owner` — `{"pid":…,"started":…}`, JSON из
  `nanoflow_model` без перевода строки, — а `release()` обрезает файл до
  нуля, перед тем как закрыть. Пустой файл — владельца нет. Запись идёт с
  позиции 0, и затем файл обрезается по длине записи: прежний владелец
  виден, пока не записан новый, и хвоста более длинной старой записи не
  остаётся (`FileMode.append` в Dart лишь один раз встаёт в конец при
  открытии, поэтому позицию можно поставить в 0). Переименовывать файл
  нельзя: блокировка привязана к открытому файлу. Без `owner` store файл
  не заполняет и очищает: оставшаяся запись прежнего владельца назвала бы
  владельцем процесс, которого нет. Кто владелец, store не узнаёт сам, ему
  его передают; от `nanoflow_process` store не зависит.
- **Читать `.owner.lock` из процесса-владельца нельзя.** Любое чтение файла
  в самом процессе, который держит блокировку, — открыл и закрыл, например
  `File.readAsString` — закрывает ещё один дескриптор этого файла и тем самым
  молча снимает блокировку процесса: другой процесс после этого может взять
  сессию, хотя первый её ведёт. Запись владельца поэтому читает процесс,
  который сессию не ведёт: так делает UI через `nanoflow_reader`.
- **`SessionHandle`** — одна сессия. Чтение: `events` (только дописанные
  строки; строка, которая не JSON-объект, — `StoreCorruptedException` с путём
  и номером строки), `steps` (в порядке создания), `documentValue`. Запись:
  `createStep` (запись шага `steps/<время>-<имя>-<id>/step.json` с ключом,
  предшественником и местом, без события), `appendEvent` (`KnownEvent`
  строкой с `\n`, сброшенной на диск; события, данные разом — шагами,
  идущими рядом, — дописываются по одному в порядке вызовов: файл, открытый
  на дописывание, пишется туда, где был конец при открытии, и два
  дописывания разом затёрли бы друг друга), `writeDocument`, `setStepOutput`,
  `setStepAfter` (шаг выполняется заново после другого предшественника),
  `openLog` (`StepLog` дописывает `step.log` в фоне: что добавлено, пока идёт
  запись, уходит после неё одной записью, а `unwritten` говорит, сколько ещё
  не записано; ошибок файла — не открылся, диск полон — не бросает ни сразу,
  ни потом: первую отдаёт `failed`, и лог больше не пишет).
- **Запись без половинок.** Файлы пишутся под временным именем с точкой и
  переименовываются; сессия и шаг собираются в `.tmp-<id>` и
  переименовываются целиком. Эти временные имена читатели пропускают.
- **Удалённая сессия не создаётся заново.** Каталог `runs` создаётся, если
  его нет, а каталоги сессии и `steps` — нет: если их удалили, пока процесс
  вёл сессию, `createStep` и `writeDocument` бросают `FileSystemException` и
  ничего не строят. Журнал `appendEvent` тоже не создаёт: нет `log.jsonl` —
  `PathNotFoundException`. А записав строку, проверяет, что у сессии есть
  `session.json`, — нет, `PathNotFoundException`. Так процесс узнаёт и об
  удалении, которое ещё идёт: `rm -rf` удаляет вглубь, и в то, до чего он не
  дошёл, запись удаётся.
- **Время** в именах каталогов берётся из `Clock`: у сессии — время
  создания (оно же — время `session-started`), у шага — время его создания,
  но не раньше чем через миллисекунду после предыдущего шага сессии: так
  имена сортируются в порядке создания, даже если часы не сдвинулись. Время
  остальных событий задаёт библиотека.
