# nanoflow: граф кодом — спецификация

Источник правды для реализации нового направления. Почему принято так, а
не иначе, — в [журнале решений](2026-10-02-code-first-decisions.md) (дальше
«решение N»). Где спецификация и журнал расходятся, права спецификация: она
закрывает вопросы, которые журнал оставил открытыми.

## 1. Что это

- **Воркфлоу — обычная асинхронная функция Dart.** Шаг — вызов
  `f.step('имя', () => …)`. Развилки — `if`/`switch`, петли — циклы,
  параллельность — `Future.wait`.
- **Библиотека `nanoflow` ведёт сессию в процессе приложения:** пишет журнал,
  после падения продолжает сессию, беря готовые шаги из журнала. Отдельного
  движка, протокола `--graph`/`--input`/`--call`, YAML и `nanoflow check` нет.
- **Граф извлекается из кода статически** (`nanoflow_describe`, анализатор
  Dart) в отдельный файл графа. Исполнение от графа не зависит; приложение
  читает файл графа только чтобы положить снимок в сессию.
- **UI** читает файл графа и хранилище сессий и показывает граф, сессии и
  шаги. UI ничего не запускает и не знает, на каком языке написан граф.

## 3. Каталог проекта

**Каталог проекта** — каталог, где лежат файл графа `nanoflow.graph.json` и
каталог сессий `runs/`.

- При разработке это корень пакета приложения (где `pubspec.yaml`):
  `describe` пишет туда файл графа, библиотека пишет туда `runs/`.
- У собранного приложения это каталог бинарника: `stamp` кладёт туда копию
  файла графа, библиотека пишет туда `runs/`.

Библиотека находит каталог проекта так: `Flow(directory: …)`, если задан;
иначе в собранной программе (`const bool.fromEnvironment('dart.vm.product')`)
— каталог `Platform.resolvedExecutable`; иначе — ближайший к
`Platform.script` предок с `pubspec.yaml`, а если такого нет — каталог
`Platform.script`.

## 4. Библиотека `nanoflow`

### 4.1. API

```dart
final flow = Flow()                     // каталог проекта — §3
  ..addCodec(Change.fromJson)
  ..addCodec(Report.fromJson);

final session = await flow.start(review, 'feature/parse-config');
print(session.id);
final result = await session.result;   // результат функции воркфлоу

// то же одной строкой:
final result2 = await flow.run(review, 'feature/parse-config');

// после падения процесса:
final again = await flow.resume(review, sessionId);
await again.result;

// незаконченные сессии воркфлоу:
final ids = await flow.unfinished(review);

flow.stop();   // остановить сессии этого Flow: их программы exec убиваются, шаги больше не стартуют
```

```dart
Future<String> review(Flow f, String branch) async {
  final change = await f.step('collect', () => git.changeOf(branch));
  …
}
```

- `Flow({String? directory})`; `addCodec<T>(T Function(Map<String, Object?>) fromJson)`.
- Функция воркфлоу: `Future<R> Function(Flow f, I input)`. Внутри неё `f` —
  тот же `Flow`: шаг находит свою сессию по зоне.
- `start<I, R>(workflow, I input)` → `Future<FlowSession<R>>`: сессия
  создана и записана, функция запущена; `FlowSession.id`, `FlowSession.result`.
  `run` = `start` + `result`.
- `resume<I, R>(workflow, String sessionId)` → `Future<FlowSession<R>>`.
  Законченная сессия не выполняется: `result` сразу отдаёт сохранённый
  результат или сохранённую ошибку.
- `unfinished(workflow)` → id незаконченных сессий этого воркфлоу.
- `step<T>(String name, FutureOr<T> Function() body)` → `Future<T>`.
  Вне сессии — `StateError`.
- Имя воркфлоу — имя функции. Библиотека узнаёт его из `toString()`
  замыкания функции верхнего уровня или статического метода
  (`Closure: (Flow, String) => Future<String> from Function 'review': static.`
  — так и под `dart run`, и в собранной программе); если имя не извлечь —
  `ArgumentError`: воркфлоу — функция верхнего уровня или статический метод.
  UI сопоставляет сессию с воркфлоу файла графа по имени: id воркфлоу
  кончается на `#<имя>` или `.<имя>`.

### 4.2. Что требуется от кода

- Шаг вызывается как `f.step(…)` внутри сессии.
- Вход воркфлоу, результат воркфлоу и результат шага превращаются в JSON
  (§4.4).
- Всё остальное свободно (решение 3). Сохраняются только шаги; код между
  шагами при продолжении выполняется заново.

### 4.3. Ключи шагов

Ключ находит сохранённый результат шага при продолжении. Устройство —
решение 1, доказательство — `prototypes/step_keys`.

- Код сессии идёт в зоне библиотеки. У каждого исполняемого кусочка есть
  **контекст** — строка; у корня сессии — `""`.
- Каждый обратный вызов, который код регистрирует в зоне в контексте `c`,
  получает свой контекст с номером, по двум независимым счётчикам, — по
  числу аргументов обратного вызова:
  - с аргументом (продолжение асинхронной функции — одно на вызов, при
    первом `await`; `then`; `onData`/`onError` потока) — `h(c + "/~" + k)`;
  - без аргумента (`Timer`, `Future.delayed`, `scheduleMicrotask`,
    `Future(…)`, `whenComplete`, `onDone` потока) — `h(c + "/~t" + k)`;

  `k` — номер среди зарегистрированных этого рода в `c`, с 1. Сама постановка
  микрозадачи или таймера в очередь номера не берёт: функция идёт в
  контексте того, кто её поставил (так продолжение `await` уже завершённого
  future не сдвигает номера). Обратные вызовы без аргумента считаются
  отдельно, потому что потоки Dart ставят служебные микрозадачи в
  зависимости от тайминга — от них не должны сдвигаться номера вызовов
  функций и копий.
- Гарантия: ключ шага одинаков при любом тайминге, если на пути к нему
  (по контекстам) последовательность регистраций не зависит от тайминга.
  Нарушают её: код, который сам решает по таймингу (`Future.any`, гонки);
  шаг, вызванный прямо из обратного вызова без аргумента (таймер,
  микрозадача, `async*`-генератор после `yield`), созданного в контексте,
  который читает поток с внешним темпом. Такие шаги при продолжении могут
  выполниться заново; чужой результат они не получают (§4.6).
- Шаг с именем `N`, вызванный в контексте `c`, получает номер `n` — который
  по счёту шаг с этим именем в `c` — и ключ `N#n@` + `h(c)`.
- Вызов функции, возобновлённый ровно результатом шага (тот же объект, что
  вернул шаг), получает контекст, равный ключу этого шага.
- `h(s)` — первые 16 шестнадцатеричных знаков sha256 от UTF-8 строки `s`.
- Шаг из журнала и шаг вживую ставят в очередь в контексте вызова одно и
  то же, чтобы номера после продолжения не сдвигались:
  - тело шага с ключом `K` выполняется в контексте `h(K + "/~0")` — не в `K`:
    иначе обратные вызовы тела делили бы счётчик `K` с кодом, который примет
    результат шага, а у шага из журнала тела нет;
  - будущее, которое возвращает `f.step`, принадлежит зоне, из которой
    сессия запущена, а не зоне ключей: позднее `await` уже завершённого шага
    не ставит в очередь лишнего в контексте вызова.
- У шага есть **предшественник** (`after`) — ключ последнего шага, результат
  которого принял контекст, где шаг вызван; `null`, если такого нет. Новый
  контекст обратного вызова наследует предшественника родителя.

### 4.4. Кодеки

- JSON-типы (`null`, `bool`, `int`, `double`, `num`, `String`, `List` и
  `Map<String, …>` из них) проходят как есть.
- Свой тип — `addCodec(Report.fromJson)`. Регистрация `T` регистрирует и
  `T?`, `List<T>`, `Map<String, T>`. Кодируется `jsonEncode` (он вызывает
  `toJson()`), раскодируется зарегистрированной функцией.
- При первом выполнении шага (и для входа и результата воркфлоу) значение
  кодируется, раскодируется обратно и проверяется `is T`. Нет кодека, нет
  `toJson`, не сходится — шаг падает с `CodecException` (сообщение называет
  тип); это обычное исключение шага.
- При продолжении сохранённое значение шага, которое больше не
  раскодируется нынешним типом (класс изменили), — чужой результат: шаг
  выполняется заново в прежней записи. Сохранённый вход воркфлоу, который не
  раскодируется, — ошибка `resume` (`CodecException`), в сессию ничего не
  пишется.

### 4.5. Лог шага и внешние программы

- `print` внутри тела шага пишет строку в лог этого шага (`step.log`).
  `print` вне шагов идёт в обычный `print`.
- `exec(executable, arguments, {workingDirectory, environment})` →
  `Future<String>` (stdout). Поведение `exec` из нынешнего пакета сохраняется
  (группа процессов, обёртка perl с SIGPIPE по умолчанию, остановка группы
  SIGTERM, через 5 с SIGKILL, `ExecException` при ненулевом коде), с двумя
  изменениями:
  - stderr программы дописывается в лог того шага, внутри которого вызван
    `exec`; вне шага — в `stderr` процесса;
  - программа умирает вместе с процессом приложения: обёртка следит за
    трубой от процесса и, когда та закрылась, останавливает группу.
- `flow.stop()` останавливает группы `exec`, запущенных в сессиях этого
  `Flow`. Программа, запущенная вне сессии, умирает вместе с процессом.

### 4.6. Ход сессии

**Создание (`start`).** Вход кодируется (§4.4) → сессия создаётся целиком,
атомарно: `session.json`, документ входа, журнал с `session-started`. Потом
берётся блокировка сессии, потом запускается функция.

**Шаг вживую.** Ключ (§4.3) не найден среди готовых:
1. запись шага (`step.json`, каталог) — если шага с этим ключом ещё нет в
   сессии; иначе используется прежняя запись;
2. `step-started`;
3. тело выполняется в собственном контексте; `print` — в лог;
4. успех → проверка кодека → документ выхода → `step-finished` →
   `step.json` с `outputId`; исключение → `step-failed` с текстом и стеком,
   исключение уходит в код воркфлоу.

**Шаг из журнала.** Ключ есть среди шагов с `step-finished` **и**
записанный предшественник (`after`) этого шага равен предшественнику
нынешнего вызова → значение раскодируется из документа, тело не
выполняется, в журнал ничего не пишется. Ключ совпал, а предшественник нет —
шаг выполняется вживую (новая запись шага не создаётся, если запись с этим
ключом уже есть, — пишется новый `step-started` в неё): лучше повторить шаг,
чем отдать ему чужой результат.

**Конец.** Функция вернула значение → документ результата →
`session-finished`. Бросила → `session-failed` с текстом и стеком.

**Продолжение (`resume`).** Блокировка → журнал читается (обрезается
недописанная строка) → готовые шаги (по `step-finished`) становятся картой
«ключ → документ» → `session-resumed` с хэшем кода и, если хэш не совпал с
последним записанным, новым снимком графа документом → функция запускается
заново с сохранённым входом. Упавший или незавершённый шаг выполняется
заново и пишет новый `step-started` в ту же запись шага.

**Повтор шага в прежней записи** (упавший, незавершённый или с другим
предшественником): сначала `step-started`, потом `step.json` переписывается
с нынешним `after` — предшественник записи может меняться.

**Блокировка.** Сессию ведёт один процесс: исключительная блокировка ОС на
`<сессия>/.owner.lock` от создания или открытия до конца сессии; ОС снимает
её при падении. Занятая сессия → `SessionBusyException` — и когда ею
владеет этот же процесс (блокировки ОС действуют на процесс, поэтому
библиотека помнит свои сессии сама). Продолжение упавшей сессии →
`SessionFailedException` с сохранённым текстом ошибки и стеком.

**Сбой хранилища.** Не удалось записать или прочитать сессию → дальнейшие
шаги не стартуют (`f.step` бросает `StorageException`), программы `exec`
останавливаются, `result` завершается с `StorageException`. После сбоя в
сессию ничего не пишется.

**Остановка (`flow.stop()`).** Шаги больше не стартуют (`f.step` бросает
`FlowStoppedException`), программы `exec` останавливаются; в журнал ничего не
пишется — сессию можно продолжить.

### 4.7. Хэш кода и снимок графа

- **Снимок.** При создании сессии библиотека читает
  `<каталог проекта>/nanoflow.graph.json`. Есть — весь файл кладётся в
  `session.json` как `graph`; нет — `graph: null`.
- **Хэш кода.** В собранной программе — `sha256:` + sha256 байтов
  `Platform.resolvedExecutable`. Иначе — отпечаток исходников (§6.2) пакета в
  каталоге проекта. Не удалось посчитать — `null`. Пишется в
  `session-started` и `session-resumed`.

## 5. Хранение

### 5.1. Файлы

```text
runs/
  review-2026-10-03T10-00-00-<id>/        сессия: <воркфлоу>-<время создания>-<id>
    session.json
    log.jsonl                              журнал сессии
    .owner.lock                            блокировка (читатель пропускает точечные имена)
    documents/<id>.json
    steps/
      2026-10-03T10-00-00-482-collect-<id>/
        step.json
        step.log
```

- Время в именах — UTC, у шага с миллисекундами; монотонно растёт в пределах
  сессии. Имя шага в имени каталога — знаки вне `[A-Za-z0-9._-]` заменены на
  `_`.
- Каталог находят по id — последние 36 знаков имени.
- Атомарная запись: временное имя с `.` в том же каталоге и переименование.
  Сессия строится целиком под `runs/.tmp-<id>/` и переименовывается.
- JSON-файлы — с отступом 2 пробела и переводом строки в конце; `log.jsonl` —
  по объекту в строке.

### 5.2. Модели

У модели всегда есть все поля; нет значения — `null`. Id — UUID v4.

| Модель | Поля по порядку |
| --- | --- |
| Сессия | `id`, `workflow` (имя функции), `graph` (снимок файла графа или `null`), `inputId` |
| Шаг | `id`, `sessionId`, `name`, `key`, `after`, `place`, `outputId`, `log` (`"step.log"`) |
| Документ | `id`, `sessionId`, `value` |

`place` — место вызова `f.step`: `путь:строка`. Путь — относительно каталога
проекта, если файл внутри него; файл библиотеки корневого пакета
(`package:<пакет>/x.dart`) — `lib/x.dart`; иначе — как в стеке вызовов.
Берётся из кадра стека, вызвавшего `f.step`; не удалось — `null`.

### 5.3. События журнала

Поля любого события: `time` (UTC, ISO-8601, ровно три знака дробной части,
`Z`), `event`. Остальные — по событию:

| `event` | Свои поля | Когда |
| --- | --- | --- |
| `session-started` | `code` | первое событие, пишется при создании |
| `session-resumed` | `code`, `graphId` | каждое продолжение; `graphId` — документ с новым снимком графа, если хэш кода изменился, иначе `null` |
| `step-started` | `stepId` | шаг начал выполняться (вживую) |
| `step-finished` | `stepId`, `outputId` | шаг вернул значение |
| `step-failed` | `stepId`, `error`, `stack` | шаг бросил исключение |
| `session-finished` | `outputId` | функция воркфлоу вернула значение |
| `session-failed` | `error`, `stack` | функция воркфлоу бросила |

- `error` — одна строка: `toString()` исключения с переводами строк,
  заменёнными на пробелы. `stack` — текст стека.
- Незнакомое событие читается как есть; событие с неверными полями — как
  незнакомое.
- `session-finished` и `session-failed` — последнее событие сессии.

### 5.4. Состояние (проигрывание журнала)

- **Сессия:** `running` — нет последнего события; `finished`, `failed`.
  `startedAt` — время `session-started`, `finishedAt` — время последнего
  события у законченной. `codes` — хэши кода по порядку (`session-started`,
  потом каждый `session-resumed`); `graphIds` — документы снимков из
  `session-resumed`.
- **Шаг:** порядок — по первому `step-started`; `status` — `running` (после
  последнего `step-started` нет итога), `finished`, `failed`; `starts` —
  число `step-started`; `startedAt`, `finishedAt`; `error`.

## 6. Файл графа

### 6.1. Формат

`nanoflow.graph.json`, один на пакет:

```json
{
  "format": 1,
  "package": "review_example",
  "fingerprint": "sha256:7d3e…",
  "sources": { "bin/main.dart": "sha256:aa11…", "lib/review.dart": "sha256:9f2c…" },
  "builds": { "review": "sha256:c07e…" },
  "workflows": ["lib/review.dart#review"],
  "functions": {
    "lib/review.dart#review": { "name": "review", "place": "lib/review.dart:21", "body": { "nodes": [], "edges": [] } }
  },
  "warnings": [ { "place": "lib/review.dart:40", "message": "steps in a closure passed on are not drawn" } ]
}
```

- `functions` — функции с шагами, по id `путь#имя` (метод — `путь#Класс.имя`).
  Граф функции описан один раз, сколько бы раз её ни вызывали.
- `workflows` — функции, переданные первым аргументом в `Flow.start`,
  `Flow.run` или `Flow.resume`.
- `body` — граф одного уровня:

```json
{
  "nodes": [
    { "id": "1", "kind": "step",   "name": "collect",             "place": "lib/review.dart:22" },
    { "id": "2", "kind": "fork",   "label": "change.path.isEmpty", "place": "lib/review.dart:23" },
    { "id": "3", "kind": "call",   "functions": ["lib/release.dart#publish"], "place": "lib/release.dart:23" },
    { "id": "4", "kind": "copies", "label": "pkg in packages",     "place": "lib/release.dart:20", "body": { "nodes": [], "edges": [] } }
  ],
  "edges": [
    { "from": null, "to": "1", "label": null },
    { "from": "2",  "to": "3", "label": "true" },
    { "from": "2",  "to": null, "label": "false" }
  ]
}
```

- `from: null` — вход тела, `to: null` — выход из тела (`return` или конец).
- Узлы: `step` (вызов `f.step`, `name` — литерал имени или исходник
  выражения), `fork` (условие; `label` — исходник), `call` (вызов функции с
  шагами; несколько `functions` — реализации интерфейса), `copies` (тело,
  которое `Future.wait` выполняет копиями: `for` внутри списка или `map`;
  `label` — `<переменная> in <выражение>`; `body` — тело копии).
- Подписи рёбер из развилки: `if`, `while`, `for(;;)`, `&&`/`||`,
  `?:` — `true`/`false`; цикл `for … in` — `each`/`done`; `switch` —
  исходник случая или `default`. У остальных рёбер `label: null`.
- Несколько рёбер из одного узла без подписи или с одной подписью —
  разветвление `Future.wait` над списком; узел, в который входят ветки, ждёт
  все.
- `place` — `путь:строка` относительно корня пакета.
- id узлов — строки, уникальные в пределах тела.

### 6.2. Отпечаток исходников

Исходники пакета — файлы `.dart` под `lib/` и `bin/`, кроме каталогов,
начинающихся с `.`, и `build/`. Для каждого: путь относительно корня пакета
(через `/`) и `sha256:` + sha256 содержимого с `\r\n` → `\n`. Строки
`<путь> <хэш>\n`, отсортированные по пути, хэшируются целиком →
`fingerprint`. `sources` — хэши файлов по пути.

### 6.3. `builds`

`stamp <бинарник>` дописывает `builds[<имя файла бинарника>] = sha256 байтов`.

## 7. `nanoflow_describe`

```text
dart run nanoflow_describe            # пишет nanoflow.graph.json в корне пакета
dart run nanoflow_describe --watch    # и перезаписывает при каждой правке исходников
dart run nanoflow_describe --check    # код 1, если файл не совпадает с тем, что был бы записан
dart run nanoflow_describe stamp build/review   # §6.3; копия файла графа рядом с бинарником
```

- Запускается из корня пакета (или с `--package <каталог>`).
- `stamp` сначала проверяет, что `fingerprint` файла совпадает с исходниками,
  иначе — код 1 и ничего не пишет.
- `--watch` печатает строку на каждую перезапись и на каждую ошибку
  разбора; файл с ошибками компиляции не перезаписывается.
- Пишет файл, только если содержимое изменилось.

### 7.1. Извлечение

По исходникам `lib/` и `bin/` с разрешением типов (`package:analyzer`),
выполнения кода нет. Метод, функция или замыкание, где есть вызов
`Flow.step` (из `package:nanoflow`) или вызов функции с шагами, — функция с
шагами. Граф тела — граф потока управления, сведённый к узлам §6.1:

- последовательность, `if`/`else`, `if-case`, `switch` (исчерпывающий по
  `enum`, `bool`, `sealed` — без `default`), `while`, `do`, `for(;;)`,
  `for … in`, `break`/`continue`, `return`, `?:`, `&&`/`||` с шагами справа;
- `Future.wait` над списком: элементы — ветки; элемент `for` — `copies`;
  `Future.wait(xs.map((x) async {…}))` — `copies`;
- замыкание, вызванное на месте, — его тело на месте вызова;
- вызов функции с шагами из исходников пакета — узел `call`; вызов метода
  интерфейса — `call` со всеми реализациями из исходников пакета;
- развилка, у которой все исходы ведут в одно и то же, не рисуется;
- `try` — тело и `finally`; ветки `catch` не рисуются (предупреждение).

Предупреждения (`warnings`): имя шага — не литерал; шаги в замыкании,
переданном дальше; вызов функции с шагами вне исходников; `catch`.

## 8. Чтение (`nanoflow_reader`)

`FsReader(<каталог проекта>)`: лента изменений сессий в `runs/` и данные по
запросу.

| `change` | Свои поля |
| --- | --- |
| `session-added` | `session` |
| `step-added` | `step` |
| `step-changed` | `step` (появился `outputId`) |
| `event-added` | `sessionId`, `event` |
| `document-added` | `sessionId`, `documentId` |
| `log-corrupted` | `sessionId`, `line`, `text` |

По запросу: значение документа, лог шага (накопленный, потом дописанное).
События сессии — в порядке журнала; недописанное не выдаётся. Сессия
закончена, когда прочитано последнее событие.

## 9. UI

Меняется по решениям 6, 8, 10, 11 и разделу 12 журнала:

- **Открыть** — файл `nanoflow.graph.json` (стартовый экран и недавние).
  Сессии — `runs/` рядом. Файл перечитывается при изменении.
- **Граф** — функции воркфлоу файла; одна — сразу, несколько — выбор.
  Узлы `call` — плитка-стопка функции; двойной клик — граф функции, путь
  вверху; кнопка на плитке — раскрыть на месте в рамке с серой обводкой.
  `copies` — рамка-стопка с подписью и `×N`, переключатель копий
  («все» и номера).
- **Свежесть.** Есть исходники рядом — UI считает отпечаток (§6.2 по
  `sources` файла) и подсвечивает «граф может не соответствовать коду» со
  списком изменённых файлов. Рядом лежит бинарник из `builds` — сравнивает
  его хэш. Предупреждения файла — списком.
- **Сессия** — граф из её снимка (последний из `session-resumed` или из
  `session.json`); хэш кода сессии ищется среди `fingerprint`/`builds`
  снимка: не нашёлся — «сессия шла на другом коде», `null` — «не проверено».
  Нет снимка — граф из файла, с отметкой «у сессии нет снимка».
- **Шаги на графе** — по `place` шага: узел `step` с тем же местом (путь
  сравнивается по окончанию). Шаг без места или без узла — в списке «не на
  графе».
- **Копии.** Копия рамки `copies` — цепочка шагов внутри рамки по `after`:
  первый шаг копии — тот, чей предшественник вне рамки; номер копии — по
  времени первого `step-started`. Подсказка — начало значения выхода первого
  шага.
- **Логи** — шаги сессии по первому `step-started`; при выбранной копии —
  её шаги. Строк «унаследовано» и «прогон разделился» нет.
- **Окно шага** — выход, лог, место в коде, ошибка со стеком; входа нет.
- Уходят: запуск программ графа, `nanoflow check`, поиск `PATH`, выбор
  `.yaml`, переключатель прогонов.
