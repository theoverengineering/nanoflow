# Владелец сессии: кто ведёт сессию и жив ли он

Дополнение к [дизайну code-first](2026-10-03-code-first-design.md). Сейчас UI
не отличает упавший процесс от идущего: незавершённая сессия выглядит как
«Running», пока журнал не кончится. Блокировка `.owner.lock` знает правду, но
UI её не трогает (и не должен — ожидание блокировки мешало бы `--resume`).

**Цель.** Процесс-владелец пишет в `.owner.lock` свой pid и время старта —
уникальный ключ процесса. Читатель по этому ключу узнаёт у ОС, жив ли
владелец, и подписывается на выход процесса; UI реактивно, без опроса,
показывает упавшую сессию «Interrupted».

Разрабатываем только под macOS; другие ОС — отдельными адаптерами потом,
архитектура это позволяет.

## 1. Решения

1. **Ключ владельца — pid и время старта процесса.** pid один не уникален:
   ОС отдаёт номер умершего процесса другому. Время старта пишет сам
   владелец: только в момент записи известно, что pid его.
2. **Падение — по уведомлению ОС**, не опросом и не ожиданием блокировки.
   Ожидание блокировки читателем на миг берёт её и может отказать
   одновременному `--resume`; опрос — не событие.
3. **Порт ОС и адаптеры.** Пакет `nanoflow_process`: интерфейс `Processes`
   (время старта процесса, его выход) и адаптеры: macOS (FFI к libc) и «не
   поддерживается» (остальные ОС). Новая ОС — новый адаптер, остальное не
   меняется.
4. **«Кто я» — дело среды выполнения, не хранилища.** Библиотека `nanoflow`
   один раз на процесс узнаёт свой pid и время старта через порт и отдаёт
   хранилищу как данные. Хранилище только пишет и очищает `.owner.lock`; от
   `nanoflow_process` оно не зависит.
5. **Наблюдение за владельцем — дело читателя хранилища.** Для файлов на этой
   машине «владелец жив» = «жив локальный процесс», поэтому `FsReader`
   получает порт `Processes` в конструкторе (по умолчанию — адаптер этой ОС).
   Другое хранилище (БД) узнавало бы своим способом и давало бы то же
   изменение ленты.
6. **UI про ОС не знает.** Он получает изменение `owner-changed` из ленты.

## 2. Формат `.owner.lock`

```json
{"pid": 4242, "started": "2026-10-03T07:43:34.651Z"}
```

- Ключи в этом порядке, оба всегда есть. `started` — время старта процесса
  от ОС, UTC, ровно три знака дробной секунды (как время событий), отброшены
  младшие разряды; `null`, когда адаптер ОС его не знает.
- Пустой файл (или его нет) — владельца нет: сессия отпущена, или её писала
  прежняя версия.
- **Запись.** Взяв блокировку, владелец пишет JSON с позиции 0 и обрезает
  файл по его длине (без промежуточного пустого файла). Переименовывать
  нельзя: блокировка привязана к открытому файлу. Читатель, заставший запись,
  получает не-JSON (новое начало и хвост старого) и ждёт следующего события.
- **Отпуск.** Перед тем как отпустить блокировку, владелец обрезает файл до
  нуля.
- **Блокировка — байт `2^30`**, а не весь файл: содержимое не под
  блокировкой и читается и там, где блокировки обязательные (Windows).
  Блокировка всего файла прежней версии этот байт покрывает — они по-прежнему
  исключают друг друга.

## 3. Порт ОС (`nanoflow_process`)

```dart
abstract interface class Processes {
  /// Адаптер этой ОС: macOS — [MacProcesses], иначе — [UnsupportedProcesses].
  factory Processes.forPlatform();

  /// Умеет ли адаптер узнавать время старта и выход процессов.
  bool get supported;

  /// Время старта процесса [pid] по ОС, UTC, до миллисекунд; `null`, если
  /// процесса нет или адаптер не умеет.
  DateTime? startOf(int pid);

  /// Завершается, когда процесса [pid] нет: сразу, если его нет уже.
  /// У неподдерживаемого адаптера не завершается никогда.
  Future<void> exitOf(int pid);

  /// Останавливает наблюдение; ждущие [exitOf] больше не завершатся.
  Future<void> close();
}
```

- **macOS.**
  - `startOf` — `sysctl({CTL_KERN, KERN_PROC, KERN_PROC_PID, pid})`;
    `kinfo_proc.kp_proc.p_starttime` (timeval в начале структуры); размер
    ответа 0 — процесса нет.
  - `exitOf` — kqueue: `EVFILT_PROC` + `NOTE_EXIT`, `EV_ADD | EV_ONESHOT`.
    Регистрация — из вызывающего изолята (`kevent` без ожидания); ожидание —
    в одном фоновом изоляте на адаптер (блокирующий `kevent`), он шлёт pid
    вышедших процессов через `SendPort`. Нет процесса (`ESRCH`) — завершается
    сразу. `close` будит фоновый изолят событием `EVFILT_USER` и закрывает
    kqueue.
- **Не поддерживается.** `supported == false`, `startOf` — `null`, `exitOf`
  не завершается.
- **Фейк для тестов** (`package:nanoflow_process/testing.dart`): процессы
  задаются вручную, выход — вызовом `exit(pid)`.

## 4. Запись владельца

- `nanoflow_model`: `Owner {pid, started}` (`toJson`/`fromJson`, порядок
  ключей); константа места блокировки `ownerLockOffset = 1 << 30`.
- `nanoflow_store`: `FsStore(runsDir, {Owner? owner})`. `lockSession` берёт
  блокировку байта `ownerLockOffset` и пишет `owner` (без `owner` — файл
  пуст, как сейчас); `unlockSession` обрезает файл и закрывает его.
- `nanoflow`: `Flow` узнаёт владельца один раз на процесс —
  `Owner(pid: pid, started: Processes.forPlatform().startOf(pid))` — и
  отдаёт его `FsStore`. API `Flow` (§4.1) не меняется: тесты сверяют запись
  с тем же адаптером ОС.

## 5. Наблюдение в читателе

Изменение ленты:

```json
{"change": "owner-changed", "sessionId": "…", "owner": {"pid": 4242, "started": "…"}, "alive": true}
```

- `owner` — запись из `.owner.lock` или `null`.
- `alive`:
  - `true` — процесс с этим pid и этим временем старта идёт;
  - `false` — владельца нет, или процесс вышел, или pid у другого процесса;
  - `null` — неизвестно: адаптер не поддерживается или `started == null`.
- **Когда.** Для сессии, журнал которой не кончился: в первом чтении — после
  её событий; потом при каждой смене пары (`owner`, `alive`). Кончилась
  сессия — `owner-changed` для неё больше нет.
- **Как.**
  - Каждый проход сканера читает `.owner.lock` незавершённых сессий (файл
    маленький). Не JSON — как в прошлый раз (дописывается).
  - Новый владелец: сначала подписка `exitOf(pid)`, потом проверка
    `startOf(pid) == started` (вышел между ними — подписка завершится сразу;
    pid чужой — `alive: false`).
  - Выход процесса: читатель сперва проходит сессию (журнал до конца — так
    штатно законченная сессия даёт `session-finished`, а не мигает
    «Interrupted»), потом, если сессия не кончилась, — `owner-changed` с
    `alive: false`.
- `FsReader({runsDir, pollInterval, Processes? processes})`: свой адаптер
  (по умолчанию) читатель закрывает, когда лента отменена; переданный —
  закрывает вызывающий.

## 6. UI

- Сессия, журнал которой не кончился:
  - `alive: false` — **«Interrupted»**: на карточке и в шапке сессии вместо
    «Running for …»; время — от старта до последнего события журнала;
    подсказка «The process that ran this session is gone; resume it to
    finish.»; шаг, который шёл, — прерван (как прерванный запуск сейчас), не
    крутится; в Logs у него иконка прерванного.
  - `alive: true` или `null`, или `owner-changed` ещё не пришло — как
    сейчас.
- Переход реактивный: пришло `owner-changed` — карточка, шапка, граф и Logs
  перерисованы без действий пользователя.

## 7. Тесты

- `nanoflow_process` (macOS, настоящие процессы):
  - `startOf` своего pid не `null`, стабилен, не позже «сейчас»; нет
    процесса — `null`;
  - `exitOf` дочернего процесса завершается после `SIGKILL` (в пределах
    нескольких секунд) и после обычного выхода; уже мёртвого — сразу;
    несколько ожиданий одного и разных pid; `close` останавливает фоновый
    изолят;
  - неподдерживаемый адаптер и фейк.
- `nanoflow_model`: `Owner`, `OwnerChanged` — JSON туда и обратно, порядок
  ключей, ошибки полей.
- `nanoflow_store`: владелец записан после взятия блокировки; без владельца
  файл пуст; отпуск обрезает файл; содержимое читается, пока блокировка
  взята; второй владелец из другого процесса по-прежнему получает
  `SessionBusyException`; запись поверх более длинной старой записи.
- `nanoflow`: в `.owner.lock` идущей сессии — pid процесса и его время
  старта по адаптеру ОС; после конца, сбоя, `stop()` — пусто; `resume` пишет
  владельца заново.
- `nanoflow_reader` (фейк `Processes`): первое чтение — `owner-changed` для
  незавершённых сессий (пустой файл → `null/false`; живой →
  `true`; чужое время старта → `false`; `started: null` или неподдерживаемый
  адаптер → `null`); выход процесса → `false`; очищенный файл → `null/false`;
  новый владелец после `--resume` → `true`; штатный конец перед выходом
  процесса — `session-finished` и ни одного `alive: false`; недописанный
  JSON — без ошибки; законченная сессия — без `owner-changed`.
- `nanoflow_reader` с адаптером macOS: дочерний процесс ведёт сессию;
  `alive: true`; `SIGKILL` → `alive: false` в пределах нескольких секунд.
- UI: «Interrupted» на карточке и в шапке, прерванный шаг на графе и в Logs,
  остановленное время; переход по `owner-changed`, пришедшему позже;
  `alive: null` — как раньше; golden карточки.
- e2e: пример, убитый `SIGKILL` посреди шага, — в ленте читателя
  `owner-changed` с `alive: false`; после `--resume` — `alive: true`, потом
  `session-finished`.
