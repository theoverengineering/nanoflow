# nanoflow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build nanoflow as specified in `README.md`, `docs/dart-graph.md`, `docs/ui-spec.md` and `docs/graph-layout.md` — engine, storage, reader, Dart graph library, examples, e2e tests and the macOS UI. The YAML graph program (`apps/nanoflow_yaml`, `nanoflow-yaml`) is **out of scope**: do not create it.

**Architecture:** A Dart pub workspace. `nanoflow_model` is the contract (models, JSON forms, storage layout, journal replay); `nanoflow_store` writes a session on disk for the engine; `nanoflow_reader` follows all sessions of a graph for the UI; `nanoflow` is the library that turns a Dart file into a graph program (`--graph`, `--input`, `--call`); `apps/nanoflow_cli` is the engine (`run`, `check`); `apps/nanoflow_ui` is a Flutter macOS app with a pure-Dart graph layout.

**Tech Stack:** Dart 3.13, Flutter 3.47 (macOS desktop), `package:test`, `package:path`, `package:args`, `package:ack` (JSON Schema), `dart:mirrors` (Dart graph library only), `file_selector`, `shared_preferences`.

**The spec is the source of truth.** Every task names the spec sections it implements. Read them in full before coding — the spec is in Russian; quote it when in doubt. When this plan and the spec disagree, the spec wins unless the plan states an explicit decision (section "Decisions" below), which then governs.

## Global Constraints

- Dart SDK constraint `^3.13.0` in every pubspec; every member has `resolution: workspace`; one root `pubspec.yaml` (workspace) and one `pubspec.lock`.
- One root `analysis_options.yaml` shared by all members; no member has its own `analysis_options.yaml`. `dart analyze` (and `flutter analyze` for the UI) must report **no issues**; `dart format` must leave files unchanged.
- Layout: `packages/nanoflow_model`, `packages/nanoflow_store`, `packages/nanoflow_reader`, `packages/nanoflow`, `apps/nanoflow_cli`, `apps/nanoflow_ui`, `examples/review`, `tests/e2e`, `tool/`, `docs/`.
- Dependency rules (README «Репозиторий»): packages never depend on apps; apps never depend on each other; the only shared package is `nanoflow_model`; `nanoflow_store` and `nanoflow_reader` never import each other; the UI imports only `nanoflow_model` and `nanoflow_reader` from this repo (never `nanoflow_store`, `nanoflow`, or `nanoflow_cli`); code under `apps/nanoflow_ui/lib/layout/` never imports `package:flutter` or `dart:ui`; no `common`-style package.
- Each package: public entry `lib/<name>.dart`, everything else in `lib/src/`, a `README.md` (Russian, short), tests in `test/`.
- Identifiers: UUID v4, lowercase, 36 chars (`8-4-4-4-12`).
- Event time: UTC ISO-8601 with exactly three fractional digits and `Z`: `2026-09-20T14:03:11.470Z`.
- Directory names (UTC): session `<graph name>-YYYY-MM-DDTHH-MM-SS-<id>`; run `YYYY-MM-DDTHH-MM-SS-mmm-<id>`; step `YYYY-MM-DDTHH-MM-SS-mmm-<node>-<id>`. File names: `runs/`, `session.json`, `documents/<id>.json`, `run.json`, `log.jsonl`, `steps/`, `step.json`, `command.log`.
- Model JSON forms, keys in this order, every key always present (`null` when no value): Session `{id, graph}`; Run `{id, sessionId, parentId}`; Step `{id, runId, inputId, outputId, log}`; Document `{id, sessionId, value}`; Event `{runId, time, event, …own fields in the README table order}`.
- Events: `run-started{node}`, `step-started{stepId,node}`, `step-finished{stepId,exitCode,outputId}`, `run-split{}`, `run-finished{}`, `run-failed{stepId,error}`.
- Changes (reader feed): `session-added{session}`, `run-added{run}`, `step-added{step}`, `step-changed{step}`, `event-added{event}`, `document-added{sessionId,documentId}`, `log-corrupted{runId,line,text}` — the discriminator key is `change`.
- CLI: `nanoflow run [--resume <session id>] -- <graph program> [args…]`, `nanoflow check [-- <graph program> [args…]]`. `run` exit codes: `0`, `1`, `2`, `128+N` exactly as in README «Запуск».
- Graph program protocol: `--graph`, `--graph --watch`, `--input`, `--call <node>` exactly as in README «Программа графа» and «Протокол команды».
- UI: English text, dark theme, local time zone, ids shortened to first 4 chars with full id in a tooltip; visuals follow `docs/design/*.html` (colors, sizes, typography) — read the HTML for exact values.
- Commit messages: imperative subject that says **why** (the problem solved or capability enabled), not what; body optional; every commit ends with the line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- TDD: write the failing test first, see it fail, implement, see it pass. Test output must be pristine (no stray prints, no warnings).

## Decisions

These fill gaps the spec leaves open. They are binding.

- **D1 — `Step.log` value.** The filesystem adapter stores `"log": "command.log"` in `step.json`: the log's file name relative to the step directory. Log text is read on request (reader `stepLog`).
- **D2 — File contents.** `session.json`, `run.json`, `step.json` and `documents/<id>.json` hold the model's JSON form, pretty-printed with two-space indent and a trailing newline. `log.jsonl` holds one compact JSON object per line, each line terminated by `\n`.
- **D3 — Atomic writes.** Files are written to a temporary name in the same directory (prefix `.`, e.g. `.step.json.tmp-<random>`) and renamed into place. A session is built whole under `runs/.tmp-<id>/` and renamed to its final name; a run (with its first step) is built under `<session>/.tmp-<id>/` and renamed. The reader ignores every name that starts with `.`.
- **D4 — First step of every run.** Every run — root or split child — is created together with its first step (run dir, `run.json`, `log.jsonl` with `run-started`, `steps/<first step>/step.json`), atomically (D3). The engine starts that step instead of creating one, also on `--resume`. (The README states this for root runs; the plan extends it to split children for uniformity.)
- **D5 — Finishing a step.** Order: write the output document (if any) → append `step-finished` → rewrite `step.json` with `outputId`. On `--resume`, a `step.json` whose `outputId` is `null` while its `step-finished` has one is repaired. `step-finished` is authoritative.
- **D6 — Later steps.** Order: create the step directory with `step.json` → append `step-started`. On `--resume`, a step directory of the run that no `step-started` references is the run's next step and is reused (at most one can exist); otherwise a new one is created.
- **D7 — Carried data.** The document that flows into a step: for the run's first step, its `inputId` if not null, otherwise (split child) the data its parent carried at the split, otherwise `null`. After a worker step the carried document is the step's `outputId` (`null` for a worker without `out`); a fork passes the carried document through unchanged. A created step's `inputId` is the carried document if its node declares `in`, else `null`. `--call` stdin gets that document's value as one-line JSON, or an empty line when the node has no `in`.
- **D8 — Outcome matching.** if-form: the outcome matches only when it is JSON `true`. switch-form: the outcome matches a key only when it is a JSON string equal to the key. Routing lives in `nanoflow_model` (`ForkNode.route`).
- **D9 — Failure texts (`run-failed.error`, one line).** Non-zero exit: `exited with code N`. Exit 0 but stdout expected and empty: `printed no output`. Exit 0 but stdout is not one JSON document: `printed invalid JSON`. switch without match and without `else`: `no target for outcome <outcome as compact JSON>`.
- **D10 — Engine stderr.** One line per event: `<HH:MM:SS local> <run id first 4> <event> <details>`; details: `run-started <node>`, `step-started <node>`, `step-finished <node> exit <code>`, `run-split <child4> <node>, <child4> <node>`, `run-finished`, `run-failed <error>`.
- **D11 — Dart graph library data and names.** Node names come from top-level variables through `dart:mirrors` (`dart run` only; no AOT). Data types between nodes are classes with a `fromJson` constructor (named constructor or factory taking the decoded JSON) and a `toJson()` method, decoded through mirrors; JSON primitives (`String`, `int`, `double`, `num`, `bool`), `List<T>`, `Map<String, T>` and enums (by name) are supported too. A parameter of type `Object?`/`dynamic` means "no `in`"; a result of `void`/`Null`/`Object?`/`dynamic` means "no `out`".
- **D12 — Dart types in the graph description.** `String`→`{"type":"string"}`, `int`→`{"type":"integer"}`, `double`/`num`→`{"type":"number"}`, `bool`→`{"type":"boolean"}`, `List<T>`→`{"type":"array","items":S(T)}`, `Map<String,T>`→`{"type":"object","additionalProperties":S(T)}`, enum `E`→`{"$ref":"#/E"}` with `types.E = {"enum":[names…]}`, class `C`→`{"$ref":"#/C"}` with `types.C = {"title":"C"}`. `command`/`decide` hold the declaration location `graph.dart:12` (path relative to the directory of the program file). Switch keys: enum → its `name`, otherwise `toString()`; `--call` prints the outcome as that key string (if-form prints `true`/`false`).
- **D13 — Process groups.** The Dart library's `exec` starts programs in their own process group through `/bin/sh -c` with job control (`set -m`), and stops them by signalling the whole group (SIGTERM, then SIGKILL after 5 s).
- **D14 — Structural check.** The graph JSON Schema (draft 2020-12) is a const Dart map in `apps/nanoflow_cli/lib/src/check/graph_schema.dart`, executed with `package:ack` (`Ack.fromJsonSchema`). If ack cannot import a keyword the schema needs, express the same rule with ack's Dart API and keep `toJsonSchema()` of it equal in meaning. Do not depend on `package:json_schema`.
- **D15 — GUI PATH.** The UI resolves `PATH` once at start from the user's login shell (`$SHELL -l -c 'printf %s "$PATH"'`, fallback to the process `PATH`) and uses it to find `nanoflow-yaml` and `nanoflow`.

**Interfaces — Produces:**

```dart
final class Target {
  const Target.node(String name);           // `then: inspect`
  const Target.list(List<String> names);    // `then: [publish, notify]`, `[]`
  final List<String> names;
  final bool isList;
  bool get isEmpty;                          // list with no names → run ends
  static Target fromJson(Object? json);      // String or List<String>; FormatException otherwise
  Object toJson();                           // String or List<String>
}

final class Exit {                           // one outgoing exit of a node, in declaration order
  final String? label;                       // null for a worker; 'true' for if; map key for switch; 'else' for else
  final Target target;
  final bool isElse;
}

sealed class Node {
  String get name;
  Object? get input;                         // `in` schema JSON or null
  String get run;                            // `command` or `decide`
  List<Exit> get exits;
}
final class WorkerNode extends Node {
  String get command; Object? get output; Target? get then;
}
final class ForkNode extends Node {
  String get decide;
  bool get isIf;                             // `then` is a target (not a map)
  Target? get ifTrue;                        // `then` of the if-form
  Map<String, Target>? get cases;            // `then` of the switch-form, insertion order kept
  Target? get otherwise;                     // `else`
  Route route(Object? outcome);
}

sealed class Route {}
final class RouteTo extends Route { final Exit exit; Target get target; }  // may be an empty list target
final class RouteEnd extends Route {}        // if-form, outcome not `true`, no `else`
final class RouteMissing extends Route { final Object? outcome; } // switch, no match, no `else`

final class Graph {
  final Target start;
  final Map<String, Object?> types;          // raw JSON, may be empty
  final Map<String, Node> nodes;             // declaration order kept
  final Map<String, Object?> json;           // the raw graph JSON it was parsed from
  static Graph fromJson(Map<String, Object?> json);  // FormatException on bad structure, never a TypeError
  Map<String, Object?> toJson();             // returns `json`
  Node? operator [](String name);
}

final class GraphDescription {
  final String file;
  final Graph graph;
  static GraphDescription fromJson(Object? json);    // FormatException on bad structure
  Map<String, Object?> toJson();
}
```

Exits order: worker `then` (if present); if-form `true` then `else`; switch keys in map order then `else`. A node with both `command` and `decide`, neither, a fork without `then`, or a worker with `else` is a `FormatException` in `fromJson` (the CLI check reports these first, through the schema).

- [ ] **Step 1:** Write failing tests: parse the README «Формат» graph (as JSON) and assert every node, exit and target; `route` for: if `true` → then; if `"true"`, `1`, `null`, `false` → else when present, `RouteEnd` when absent; switch `"accepted"` → key; switch `1` with key `"1"` → no match; no match with `else` → else exit; without → `RouteMissing`; `else: []` → `RouteTo` with empty target; malformed JSON shapes → `FormatException`; `GraphDescription` round trip.
- [ ] **Step 2:** Run — fail. **Step 3:** Implement. **Step 4:** Run — pass; analyze; format. **Step 5:** Commit.

Behaviour of `serve` (`file` = `Platform.script.toFilePath()`):
- `--graph`: build; errors → stderr one per line, exit 1; otherwise print `describe(...)` as one-line JSON + `\n`, exit 0.
- `--graph --watch`: print the description (if the build succeeds), then watch the program file's directory recursively for `.dart` changes (debounce ~200 ms) and re-run `Platform.resolvedExecutable` with `Platform.executableArguments`, the script and `--graph`; print its stdout line when the process succeeds and the line differs from the last printed one; print nothing while it fails. An exception → message and stack trace on stderr, exit 1. Stop (stdin EOF, SIGINT, SIGTERM) → stop every running `exec` process group, then exit (130 for SIGINT, 143 for SIGTERM, 1 for EOF).
- stdout is written only by the library, once, at the end of a step; flush before exiting.

`exec`: runs `executable` with `arguments` in its own process group (D13); writes `stdin` (if given) and closes it; streams the program's stderr to the process stderr as it arrives; returns its stdout decoded as UTF-8; non-zero exit → `ExecException`.
```dart
final class LayoutOptions {            // defaults taken from the mockups
  final double tile;                   // tile side
  final double cornerRadius;           // edge corner radius
  final double laneGap;                // 10
  final double portGap;                // 10 (inputs on the bar)
  final double capsuleGap;             // 14
  final double minInputStraight;       // 20
  final double arrowLength;            // arrowhead length; arrowGap = gap between tip and bar
  final double arrowGap;
  final double Function(String text, LabelKind kind) measure;  // text width; default: monospace approximation
}
enum LabelKind { exitLabel, counter, nodeName, command }

final class GraphLayout {
  final Map<String, NodeBox> nodes;    // tile rect, name/command label rects, input bar segment, layer
  final List<ExitBox> exits;           // per node exit: label, position (dot or capsule rect or stub), isElse, isEmpty
  final List<EdgePath> edges;          // from exit (and list index) to node; polyline points (H/V/45° only); kind: forward/back/loop
  final Rect bounds;
}
GraphLayout layoutGraph(Graph graph, {LayoutOptions options});
List<String> checkLayout(GraphLayout layout);   // step-9 violations as text; empty = OK
int countCrossings(GraphLayout layout);
```
