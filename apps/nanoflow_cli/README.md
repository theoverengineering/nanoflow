# nanoflow_cli

Движок — команда `nanoflow`: [`nanoflow run`](../../README.md#запуск) и
[`nanoflow check`](../../README.md#nanoflow-check).

```bash
nanoflow run -- dart run graph.dart < вход.json   # новая сессия до конца
nanoflow run --resume <сессия> -- dart run graph.dart   # продолжить сессию
nanoflow check -- dart run graph.dart   # граф из --graph программы графа
nanoflow check < описание.json          # описание графа из stdin, как его даёт UI
```

## Что внутри

- **Проверка графа** (`src/check/`). `checkGraph` даёт ошибки графа в JSON,
  по строке `<место>: <что не так>`; место — путь в графе (`start`,
  `nodes.verdict.then.accepted`, `start[1]`), у самого графа — `graph`.
  - **Структура** — JSON Schema графа (draft 2020-12, `graph_schema.dart`),
    её выполняет `package:ack` (`Ack.fromJsonSchema`). ack останавливается
    на первой ошибке, поэтому сначала проверяются ключи графа без узлов —
    ошибка там одна и останавливает проверку, — потом каждый узел отдельно:
    у каждого сломанного узла своя строка. Узел — рабочий или развилка через
    `oneOf`: `if`/`then`/`else` ack не импортирует. Когда `oneOf` не
    проходит, узел проверяется ещё раз схемой своего вида — по `command` или
    `decide`, — чтобы назвать настоящую ошибку. Ошибку, которую ack называет
    иначе, строка передаёт его словами.
  - **Смысл** — только если структура прошла: цели называют существующие
    узлы, в списке целей нет повторов и не одно имя, `start` не пуст, до
    каждого узла можно дойти от `start`. Строки — в порядке мест в графе.
  - `readDescription` читает описание графа `{file, graph}`,
    `checkDescription` проверяет его граф.
- **Программа графа** (`src/program.dart`). `GraphProgram` запускает её:
  `describe()` — `--graph`, описание с графом, прошедшим проверку;
  `graphFile()` — `--graph`, только путь к файлу графа, без проверки графа;
  `validateInput()` — `--input`; `startCall()` — `--call <узел>`. Программа
  не запустилась — `GraphProgramStartException` с причиной от системы.
- **Движок** (`src/engine/`). `Engine` ведёт все прогоны сессии разом, пока
  каждый не закончится, — каждый с того места, где он остановился: у новой
  сессии это первые шаги. `stop()` больше ничего не пишет и закрывает stdin
  всех `--call`; кто не завершился за 10 с, того убивает (SIGKILL) и
  перестаёт читать его вывод: команда в своей группе может пережить `--call`
  и держать его stdout открытым. Ctrl+C в терминале получают и `--call`:
  если вызов закончился так, как его заканчивает SIGINT или SIGTERM (убит
  сигналом или код 130, 143), а движок ещё не останавливается, прогон
  250 мс ждёт его остановки и тогда ничего не пишет. Прогон, который не
  смог записать или прочитать сессию (`FileSystemException`: каталог
  удалён, диск полон, нет прав), не падает сам по себе — и лог шага, который
  не пишется (`StepLog.failed`), тоже: первый такой сбой останавливает
  движок, как `stop()`, и `drive()` бросает эту ошибку, когда все шаги
  остановлены.
  - `recovery.dart` — где движок подхватывает каждый прогон, по журналу (он
    главный) и каталогам шагов: прогон закончен; ждёт разветвления родителя;
    берёт шаг — первый, ещё не начатый, или последний, не завершённый
    (новый `step-started` того же шага, лог дописывается); идёт дальше от
    завершённого шага. Шаг, который не назван ни в одном `step-started`, —
    первый шаг прогона или уже созданный следующий (D6); потомки
    недописанного разветвления — прогоны с его `parentId`, по узлу из
    `run-started`. Данные, которые несёт прогон, считаются заново проходом по
    его завершённым шагам от входа первого шага или от данных родителя на
    разветвлении. `step.json` без `outputId`, который назван в
    `step-finished`, получает его (D5). Что напечатал шаг, хранится только
    документом, поэтому у шага без данных после падения ошибка — `printed no
    output or invalid JSON`.
  - `run_driver.dart` — один прогон: шаг, маршрут, разветвление. Порядок
    записи: `step-started` → `--call` → документ выхода → `step-finished` →
    `outputId` в `step.json`; следующий шаг — каталог шага, потом его
    `step-started`; разветвление — все прогоны-потомки, потом `run-split`.
    Программа графа не запускается для шага — сразу за его `step-started`
    `run-failed` с `cannot start the graph program: <причина>`, без
    `step-finished`; остальные прогоны идут дальше.
  - `step_process.dart` — один `--call`: строка входа в stdin, который
    остаётся открытым; stderr (и stdout рабочего узла без `out`) — в лог
    шага по мере поступления, stdout с данными копится до завершения. Пока
    лога ждёт записи больше 1 МБ, вывод `--call` не читается: шаг, который
    пишет быстрее диска, ждёт на своём канале, а не копится в памяти
    движка.
  - `carried_data.dart` — какие данные идут по прогону: вход шага, если у
    узла есть `in`; после рабочего узла — его выход, развилка передаёт
    данные дальше как есть.
  - `progress.dart` — строка в stderr на событие:
    `<ЧЧ:ММ:СС> <4 знака id прогона> <событие> <подробности>`.
  - `run_command.dart` — `nanoflow run`: граф из `--graph` и его проверка,
    вход через `--input` (только если он нужен узлам `start`), сессия, id
    сессии в stdout, коды 0, 1 и 2. Сессию не удалось записать или
    прочитать — одна строка `cannot store the session: <что> <путь>:
    <причина>` в stderr и код 2, если сессию не удалось создать или открыть,
    иначе 3. С `--resume` — только путь к файлу графа
    из `--graph`, сессия рядом с ним идёт по своему сохранённому графу, stdin
    не читается. Пока движок ведёт сессию, он держит её блокировку
    (`nanoflow_store`): `--resume` сессии, которую ведёт другой движок, —
    `session <id> is being run by another engine` в stderr и код 2, в
    сессию ничего не пишется. Пока движок ведёт сессию, первый SIGINT или
    SIGTERM вызывает `stop()`, код — `128 + N`.
- **Команда** (`src/cli.dart`, `src/check/check_command.dart`). У `check`
  ошибки — в stdout по одной в строке, код 0, если граф прошёл, иначе 1. Нет
  описания — одна строка `cannot read the graph: <причина>`; stderr
  программы графа идёт в stderr. Не те аргументы — usage в stderr, код 2.
- **stdin процесса** (`src/stdin.dart`) — вход `run` и описание для `check`
  — читается из самого fd 0 через `read(2)` (`dart:ffi`) в отдельном
  изоляте, где ожидание входа ничего не держит; fd 0 не закрывается.
  `stdin` из `dart:io`, дочитав, закрывает fd 0 в другом потоке: программа,
  которую движок запускает в этот момент (`--input`), могла получить
  закрытый stdin и не завершиться никогда. Так читается любой stdin: файл,
  канал, терминал, `/dev/null`, сокет (его даёт родитель на Node.js) и
  неблокирующий — на `EAGAIN` чтение повторяется после короткой паузы
  (`poll(2)` на macOS не работает с терминалами). Процесс запущен с
  закрытым stdin (`<&-`) — fd 0 тогда занимает сама VM Dart (у него, в
  отличие от унаследованного, стоит close-on-exec), его не читают: stdin
  пуст, у `run` это `no input on stdin`. stdin не читается (например,
  каталог) — `cannot read stdin: <причина>` и код 2 (у `check` —
  `cannot read the graph: stdin: <причина>`).

## Тесты

```bash
dart test
```

Программы графа в тестах — короткие скрипты `sh` во временном каталоге;
общие помощники — в `test/support/`. Тесты движка идут через
`FakeProgram` (`test/support/fake_program.dart`): программа графа на `sh`,
у которой каждый узел — скрипт `nodes/<узел>.sh`; конец stdin `--call`
убивает скрипт с его группой процессов. Помощники для сессий на диске
(журнал прогона, шаги, логи, строки stderr) — в
`test/support/sessions.dart`. Тесты `--resume` строят сессию, оборванную
на нужном месте, через `nanoflow_store`. Тесты сигналов один раз компилируют
`nanoflow` (`dart compile exe`, `test/support/compiled.dart`) и шлют сигнал
его процессу или, как Ctrl+C, всей его группе процессов. Так же
`test/engine/step_log_test.dart` меряет память процесса движка, пока шаг
пишет в лог около 200 МБ. Тесты stdin процесса запускают `nanoflow` из
исходника отдельным процессом (`nanoflowProcess` в
`test/support/helpers.dart`) с каждым видом stdin: канал, файл, сокет и
неблокирующий канал (их делает `perl`), `/dev/null`, каталог, закрытый
stdin; `test/support/fd0_after_cli.dart` после команды говорит, открыт ли
ещё fd 0.
